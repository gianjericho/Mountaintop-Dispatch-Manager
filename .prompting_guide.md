# 🤖 Prompting Guide: Dispatch Manager

To avoid **context drifting** and ensure the AI remains aligned with the project's architecture, use this guide as a "context anchor" for every new session or major feature request.

---

## 🎯 Project Essence
**Dispatch Manager** is a real-time field service coordination app. It triages incoming tickets (SLR/SLI) from Google Sheets (via Apps Script), stores them in Supabase, and dispatches them to field technicians based on Role-Based Access Control (RBAC).

## ⚓ Context Anchors (Read These First)
Before making any changes, the AI **must** keep these files in its active context:
1.  **`DATABASE_CONTEXT.md`**: The definitive source for table schemas and business logic rules.
2.  **`app.js`**: The core logic file (Frontend + Supabase integration).
3.  **`index.html`**: The UI structure (Tailwind classes, Modal IDs, and Tab navigation).

---

## 🛠️ Tech Stack & Constraints
- **Frontend**: Vanilla JavaScript (ES6+), Tailwind CSS, FontAwesome 6.
- **Backend**: Supabase (Auth, PostgreSQL, Realtime WebSockets).
- **Automation**: Google Apps Script (Bridge between Sheets and Supabase).
- **Design**: Premium, modern, dark/light mode supported. **No frameworks** (no React/Vue).

---

## ⚖️ Core Business Rules (Don't Drift!)

### 1. The SLR vs. SLI Distinction
The UI dynamically rebrands fields based on the `type` column in `service_orders`:
- **SLR**: Uses "Reported Trouble" and "Ticket No."
- **SLI**: Uses "Package Name" and "JO No."
*Always preserve this logic when touching the "Manual Dispatch" or "Edit" modals.*

### 2. Role-Based Access Control (RBAC)
- **`developer`/`admin`**: Full access to all tabs (Inbox, Active, Performance, Settings).
- **`tech`**: **Strictly limited.** Can only see 'active' tickets assigned to their specific `team`.
*When adding features, specify if they are global or role-restricted.*

### 3. The "Pending" Inbox
New tickets enter as `status: 'pending'`. Only Admins/Developers can see them. Moving a ticket to a team changes its status to `active` and sets the `dateAdded` (dispatch date).

## 💡 How to Prompt for this Project

### ❌ The Bad Way ("Context Drifting")
> "Add a new field for 'Notes' to the ticket system."
*Result: The AI might forget the SLR/SLI branch, miss the database schema in Supabase, or skip the RBAC checks.*

### ✅ The Good Way ("Context Anchored")
> "Referring to `DATABASE_CONTEXT.md`, add a new `notes` text column to the `service_orders` table. Update `app.js` to show this in the Technician view, ensuring it follows the RBAC rule that only assigned techs can edit it. Make sure to update both SLR and SLI modal layouts."

---

## 🚩 Avoiding Context Drift: Pro-Tips
- **Start New Sessions with this Guide**: Copy-paste the "Project Essence" and "Core Business Rules" sections if the AI seems to be hallucinating framework code or incorrect table names.
- **Explicitly Mention Roles**: Always state "This is for the Technician role" or "This is an Admin-only tool" to trigger the correct mindset.
- **Reference UI IDs**: Use the IDs from `index.html` (e.g., `#inbox-container`, `#main-dispatch-board`) to ensure the JS remains linked to the DOM.

---

## ⚡ Execution
The application uses the raw `app.js` file for everything.
-   Make sure your changes are purely within `app.js`.
-   There is no build process or minification required. Just save and refresh.

## 🧪 Testing (Cypress)
Standardized tests are located in `/cypress/e2e`.
-   **Run All Tests (Headless)**: `npm test`
-   **Open Cypress Dashboard**: `npx cypress open`
-   **Key Test Suites**:
    -   `dispatch_test.cy.js`: Verifies the ticket creation, approval, and completion flow.
    -   `tech_rbac_test.cy.js`: Ensures Technicians are correctly restricted to their assigned teams.
